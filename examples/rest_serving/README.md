# REST serving — trained PETRA model exposed over HTTP, every endpoint exercised

The closest thing to an end-to-end workflow-engine integration
demo without a real engine on the box. Train a small
loan-approval model, build a FastAPI app over it via
`build_app(module)`, then exercise every endpoint a non-Python
client would call — `/healthz`, `/schema`, `/forward`,
`/anomaly`, `/counterfactual`, `/sensitivity`.

For production deployment the same FastAPI app runs under
uvicorn (see the `petra-serve` CLI), behind whatever
reverse-proxy / load-balancer / TLS-terminator your platform
uses. The CLI is intentionally thin — the load-bearing logic
lives in `build_app`, which the test exercises directly via
FastAPI's `TestClient`.

## What this scenario demonstrates

End-to-end through the `petri_net_nn.rest` module:

1. **Train the model** via `load_scenario(...)` and `ctx.train()`.
   Standard PETRA pipeline.

2. **Build the FastAPI app** via
   `build_app(module, title=..., version=...)`. The function
   wires the six endpoints onto a fresh FastAPI instance and
   returns it ready to mount or hand to uvicorn.

3. **Liveness and discovery.** `GET /healthz` returns module
   stats; `GET /schema` returns the served net's structural
   inventory (places, transitions, labels, initial marking).
   A workflow engine reads `/schema` once at deploy time to
   learn what inputs and outputs the served model exposes.

4. **Per-event inference.** `POST /forward` returns
   per-transition firing activations given an input marking;
   `POST /anomaly` returns trace-level + per-transition
   residuals given an event sequence. These two are the
   day-to-day decisioning endpoints — call them per
   process-step from the engine's audit-log hook.

5. **Explanations.** `POST /counterfactual` and
   `POST /sensitivity` return regulator-facing model
   explanations on a per-decision basis. Same machinery as the
   `regulator_ready_credit_approval/` scenario, exposed over
   HTTP for non-Python consumers.

6. **OpenAPI documentation.** FastAPI auto-generates a Swagger
   UI at `/docs` and an OpenAPI JSON schema at
   `/openapi.json`. The test confirms the schema endpoint is
   reachable — that's what a client-side SDK generator (e.g.
   `openapi-generator`) consumes to produce typed clients in
   Java, C#, Go, TypeScript, etc.

## Production deployment

For an actual production deployment, the typical shape is:

```bash
# 1. Train and save a bundle (a .pt module + .meta.json sidecar).
petra-train examples/rest_serving/scenario.toml --bundle model

# 2. Serve the bundle under uvicorn on port 8000.
petra-serve model --host 0.0.0.0 --port 8000

# 3. From the engine, POST events as they happen:
curl -sX POST http://localhost:8000/forward \
     -H 'content-type: application/json' \
     -d '{"input_marking": {"p_application": 0.5}}' | jq
```

The same OpenAPI shape PETRA emits is what an autogenerated
Java / C# / Go / TypeScript client would consume, so a
workflow engine in any of those languages can call PETRA
directly without an SDK on top.

The `[rest]` / `[dev]` optional extras bring FastAPI,
uvicorn, and httpx — *the test requires `[rest,dev]`
installed*. Without them the test is skipped (the export
itself works on the base install; only the serving and
in-process testing depend on these extras).

## Why this matters

Three documented integration patterns
([INTEGRATION_PATTERNS.md](../../docs/INTEGRATION_PATTERNS.md))
let a workflow engine talk to PETRA:

1. **REST webhook** — engine POSTs to PETRA per
   event-of-interest. *This is the scenario shipped here.*
2. **Audit-log tail** — engine exports its history table as
   CSV; PETRA runs `petra-score` over it.
3. **Streaming subscription** — engine publishes to Kafka /
   RabbitMQ / Redis Streams; PETRA's `StreamingEvaluator`
   consumes (see [`realtime_monitoring/`](../realtime_monitoring/)).

Whichever pattern fits the engine's deployment shape, the
analytical core is the same.

## Files

- `scenario.toml` — net, training traces, training
  hyperparameters.
- `../../tests/scenarios/test_rest_serving.py` — trains the
  module, builds the FastAPI app, exercises each endpoint
  through `TestClient`, and pins the load-bearing assertions.

python -m pytest tests/scenarios/test_rest_serving.py
